# Glossary

These definitions explain how terms are used in this repository. They do not
replace normative clauses in [RFC-0001](./rfcs/0001-physical-bearer-cryptocurrency/README.md)
or the canonical [key lifecycle](./docs/key-lifecycle.md).

| Term | Meaning |
|---|---|
| Activation challenge | Fresh value generated by the coin for one epoch and bound into the finalized funding evidence required to enter `ACTIVE`. |
| Architecture A | Version 1 smart-account baseline. Whether balance-preserving rotation lets one account span multiple key epochs remains an open decision. |
| Architecture B | Later research candidate: a hidden hardware-held note in a shared commitment/nullifier pool. |
| AssetID | Exact chain and asset identity, including the relevant native asset or contract identity—not merely a ticker such as `USDC`. |
| `AUTH_PENDING` | Core state in which one exact monetary authorization has been durably committed. Only exact retry is currently defined; general cancellation is unresolved. |
| Backing | The represented asset balance recorded by the selected chain. A balance observation does not guarantee that a later claim will execute. |
| BSLRR | Optional Bearer-Since-Last-Rotation Record: a local root/count continuity mechanism. It is not a bearer registry, identity system, or anonymity mechanism. |
| Claim | Deliberate destination-bound authorization to move the represented value and retire the old bearer authority. |
| `ClaimIntent` | Stable monetary and customer authorization binding the account, asset, amount, destination, merchant, quote, basket, settlement, expiry, and related terms. |
| Core | The secure hardware boundary that holds monetary authority and enforces the local lifecycle. Its claims remain subject to implementation and physical evaluation. |
| `coreState` | Core-signed lifecycle state, such as `ACTIVE`, `AUTH_PENDING`, or `TAMPER_SUSPECTED`. |
| Epoch | One bounded lifecycle for a monetary key, represented load, and associated account or note authority. |
| Exact retry | Reproduction of the already committed authorization without invoking the monetary key again or changing its meaning. |
| External risk status | A signed opinion from a publisher selected by the verifier or operator. It cannot mutate the coin or universally invalidate physical transfer. |
| Finalized evidence | Output from a future proof profile anchored to a specified chain identity, authenticated checkpoint, and finality rule. No qualifying version 1 proof profile has been selected. |
| Finite generate-on-advance | Version 1 lifecycle in which the core has an irreversible maximum epoch count and generates the next key only after the previous epoch closes. |
| Handoff | Physical transfer of possession. Ordinary handoff does not require an app, account, network request, or onchain transaction. |
| Local attestation | Fresh evidence that a core accepted under the verifier's selected hardware policy answered a challenge and reported state. It does not prove the core is inside the presented shell. |
| Monetary slot | The core storage/key position used for one epoch. A retired slot cannot reactivate. “Slot” describes implementation state; “epoch” describes the corresponding protocol lifecycle. |
| Monetary key | Current non-exportable target key authorized to create narrowly defined operations for the represented value. |
| Nullifier | Architecture B's proposed public one-time value used to prevent a hidden note from being claimed twice. |
| Observed chain state | An attributed observation of account balance and status at a named block, including source and finality information. It does not guarantee that a later claim will execute. |
| Proof-activated loading | Transition to `ACTIVE` only after the core verifies slot-bound finalized evidence of the exact expected account, key, asset, amount, and beneficiary. |
| Represented amount | Exact bearer amount shown for the epoch and sent to the claim destination. Unexpected assets or same-asset surplus do not increase it. |
| Residual beneficiary | Address fixed during loading that receives same-asset surplus after claim. Who may select it and which interests it represents remain open decisions. |
| Semantic nonce | Monotonically advancing value shared by claim, rotation, migration, and later monetary operations so they cannot authorize concurrently. |
| Sealed-by-core | A device report that a key was internally generated or activated and has not undergone a claim transition or export. It is not proof against invasive extraction. |
| `TransportAuthorization` | Replaceable delivery authority binding a `ClaimIntent` digest to chain/fork, EntryPoint or relay, fee/gas caps, validity, paymaster, sponsor nonce, and an identifier or digest for the fee-failure policy. Signing that identifier records terms; it does not enforce legal loss allocation. The schema is unfinished. |
| Transparent rotation | Replacement of the monetary key while retaining a publicly linkable account relationship. |
| Version 1 | The narrow Architecture A profile defined by the current draft RFC. It is a target for valueless prototypes, not a production release. |
